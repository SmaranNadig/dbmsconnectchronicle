What this project is

Scientists publish maps of a fruit fly's brain wiring (a connectome: neurons and the synapses between them) as a series of releases. Each release corrects the last. We built a database that loads every release without overwriting the old ones, so any past version can be queried, and every fact can be traced to the file and line it came from. Releases can be compared, and the data is spread over several database servers.

NoSQL implementation (MongoDB 7)

The two datasets publish different columns (hemibrain has 3 per neuron; FlyWire has 21, spread over several files per release), and a column can appear or vanish between releases. Forcing these into fixed relational columns would mean many empty columns or frequent schema changes. So the original rows go into MongoDB as one document per neuron, and the cleaned, typed facts stay in PostgreSQL.

Document structure

{
  "_id": "hemibrain:1688868386",        // = dataset_neuron.metadata_doc_id in PostgreSQL
  "dataset": "hemibrain",
  "source_neuron_id": "1688868386",
  "dataset_neuron_id": 41903,            // PostgreSQL primary key
  "releases": {                          // one entry per release the neuron is in
    "<release_id>": {
      "release": "v1.2", "ingestion_run_id": 4, "synced_at": "…",
      "records": [ {                     // every source row about this neuron
        "file": "…/traced-neurons.csv", "sha256": "…", "line": 20241,
        "fields": { …all columns exactly as published… }
      } ]
    }
  }
}

How the two stores stay consistent

  1. A release is loaded into PostgreSQL in one transaction. Each neuron row gets metadata_doc_id.
  2. metadata sync reads the same source files and upserts one document per neuron ($set releases.<id>), so re-running it is idempotent.
  3. Each sync is logged in the PostgreSQL table metadata_sync (status, counts).
  4. metadata check compares both stores: the same neuron ids, and the same rows per release.

Distributed database: 3 shards

Horizontal fragmentation

Each neuron, with its connections, belongs to exactly one shard. Three ways of choosing the shard are compared below.

Replication

A connection between neurons on two different shards is stored on both (a mirror). The small release and neuron tables are copied to every shard.

Query routing

The router sends a query only to the shards that can hold the answer, runs them in parallel and merges the results. Every query is logged.
