# Query catalogue

These are the questions ConnectomeChronicle is built to answer. Each is
written once, in the simplest form that is correct, and then executed on the
loaded data (2 datasets, 5 releases, 182,274 neurons, 9.0 M connection rows,
182,274 MongoDB documents).

The catalogue is [`config/query_catalogue.yaml`](../config/query_catalogue.yaml),
and [`backend/design/queries.py`](../backend/design/queries.py) runs it. SQL
goes through the same path as the dashboard's query console:
- **Read-only queries** run as role `cc_reader` in a `READ ONLY` transaction.
- **Writes against the real tables** run as role `cc_tryout`, with every
  constraint and trigger, and are rolled back.
- **Lab writes** run in the editable lab schema and are rolled back.

Every query is executed twice. The first run gives the result. The second
runs under `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` and gives the plan the
database actually used. MongoDB queries are explained with
`explain("executionStats")`.

Each query also states what must hold. For example:
- the plan uses a given index;
- a large table is not read sequentially;
- the winning MongoDB plan is an `IXSCAN`;
- a write is rejected with a given error.

The result below is regenerated by `python scripts/design_docs.py queries`.
On the dashboard, **Design → Queries** runs any of them on demand, and
**Open in console** loads it into the SQL or MongoDB console to be changed.

## How the queries are written

- **Start from the most selective key.** A neuron question starts at the
  neuron: the index on `(dataset_id, source_neuron_id)`, then
  `connection_pre_idx`. It never filters the 9 M-row `connection` table
  after the fact.
- **Use the bitemporal predicates exactly:**
  - `upper_inf(tx)` means current belief;
  - `upper_inf(valid_rel)` means still valid in the latest release;
  - `valid_rel @> release_order` means valid in that release;
  - `tx @> timestamp` means as the database believed it at that time.

  The partial indexes are built on the same expressions.
- **Prefer set operations and joins to procedural loops.** Use `EXCEPT` and
  `INTERSECT`, `NOT EXISTS` (anti-join, NULL-safe), and window functions in
  place of one query per row.
- **Aggregate once and read many times.** Per-release counts come from the
  materialized view `release_stats`, which is refreshed inside the load
  transaction.
- **Keep keys in the database.** Ids are looked up with the function
  `cc.find_neuron(dataset, source id)` or a subquery, not typed into the
  query.
- **Let constraints reject bad writes.** The DML examples show the
  exclusion constraint and the append-only trigger rejecting what
  application code might otherwise let through.
- **MongoDB keeps original rows for known neurons.** Lookups go through
  `_id`, `(dataset, source_neuron_id)` or `dataset_neuron_id`, all indexed.
  Analytical questions about the connectome are answered in PostgreSQL.

#### `q-downstream`: Which neurons can be reached from hemibrain neuron 487144598 in at most two steps over strong connections (at least 50 synapses)?

```sql
WITH RECURSIVE reach(neuron, depth) AS (
  SELECT cc.find_neuron('hemibrain', '487144598'), 0
```
